# Milestone 7 - Use of LLMs

PrismPM uses LLMs where language understanding provides clear value, and deterministic code everywhere else.

| Use                           | What the model does                                                                                                           | Where                                       |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| Natural-language Assistant    | Interprets a PM's request, calls read and write tools in a loop, explains what changed                                        | `api/assistant/chat/route.ts`, `assistant/` |
| "Why did we..." answers       | Turns the output of a deterministic Decision search into a concise, cited answer, and abstains when nothing is recorded       | `WHY_RULES` in `assistant/prompt.ts`        |
| Decision extraction           | Reads Evidence and Comments and proposes Decisions with alternatives, Assumptions and verbatim excerpts                       | `proposals/extract.ts`                      |
| Task and Milestone extraction | A second call over the same sources proposes the action items and dated checkpoints the team committed to                     | `proposals/extract-items.ts`                |
| Semantic Evidence search      | An embedding model turns Evidence chunks and queries into vectors so the Assistant finds a passage by meaning, not by keyword | `search/`, ADR 0014                         |
| File transcription            | A PDF with no text layer (a scan) is transcribed by the chat model so it becomes searchable Evidence                          | `evidence/`                                 |
| Render drafting               | Condenses a brief or site notes into a visual description the PM edits before it goes to an image model                       | `renders/draft.ts`, ADR 0016                |
| Concept images                | A separate image model (Pollinations) draws the approved description                                                          | `renders/provider.ts`, ADR 0012             |
| Reflection                    | After a conversation, rewrites the User's Profile and the Project's Working Memory, both versioned and editable               | `reflection/`                               |

## Why LLMs are the right tool here

The problem PrismPM solves is that project reasoning lives in prose: meeting notes, transcripts, vendor emails, chat.
Before an LLM, the only way to get a Decision out of a transcript was for a human to read it and type it into a log, which is a recurring capture effort that is easy to let lapse.
Three properties of the task make a language model the right fit:

1. **The input is unstructured and varied.** A Decision can be phrased as "we'll go with Playwright", "approved by the sponsor" or buried in turn 9 of a transcript. Rules cannot enumerate that; the heuristic fallback we built finds 12 of 22 extraction cases against 21 of 22 for the model (M12).
2. **The output is structured and partly checkable.** The model's answer becomes a row with a verbatim excerpt, so several properties are verified mechanically (`trace.ts`, the schemas and the services): the source exists, the excerpt is verbatim, the shape is valid and the User may touch the target.
   Semantic correctness is not: a verbatim quote proves the words exist, not that the model read them right (the injected instruction in eval case `x07` is quoted verbatim). That part is measured by the eval suite (M11) and left to the PM's review.
3. **Requests span several entities.** "Plan a two-month launch with UAT in week 6" needs Milestones, then Tasks with dates, then a summary. A tool-calling loop does that in one message; a form cannot.

## Where LLMs are deliberately not used

Authorization, ownership, validation, transactions, Activity History, Decision search ranking, impact detection and graph walks are deterministic application logic.
They have one right answer, and a model would add cost and non-determinism to something already correct.

The division is intentional.
The model proposes interpretations and tool calls; the application remains the source of truth and enforces permissions, approval cards, citations and durable state.
The approval boundaries differ by path:

- A Proposal (a Decision, Task or Milestone extracted from Evidence) never becomes a record until the PM accepts it.
- A Render prompt never reaches the image provider until the PM has edited and approved it.
- An in-app Assistant write pauses at an approval card by default; a User who chooses **Always allow** for a tool in a scope removes that card for it from then on.
- Over MCP, PrismPM excludes destructive tools, and an ordinary write relies on the MCP client's own approval behaviour.
